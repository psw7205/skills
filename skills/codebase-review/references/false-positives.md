# 오탐 억제 (False Positives)

LLM 코드 리뷰의 대표 실패모드는 "그럴듯하지만 틀린 발견"의 양산이다.
아래 목록에 해당하면 발견으로 올리지 않거나, 실제 근거가 있을 때만 올린다.

## Pre-Report Gate — 발견마다 4문항

각 발견을 목록에 올리기 전에 자문한다. 하나라도 "아니오"면 강등하거나 버린다.

1. **정확한 `file:line`을 인용할 수 있는가?** — 못 하면 발견이 아니다.
2. **구체적 실패 모드를 명명할 수 있는가?** — "어떤 입력/상태에서 어떤 나쁜 결과"를 말할 수 없으면 추측이다.
3. **주변 컨텍스트를 읽었는가?** — caller, import, 관련 테스트, 상위 처리. 안 읽었으면 판단 보류.
4. **심각도를 방어할 수 있는가?** — "이걸 안 고치면 누가 어떻게 영향받는가"에 답할 수 없으면 강등.

## Quote-the-line Gate

High/Critical 발견은 evidence 첫 항목이 반드시 **verbatim 근거 라인**(실제 코드 한 줄 + `file:line`)이어야 한다.
근거 라인을 그대로 인용하지 못하면 Medium 이하로 강등한다.

## Common False Positives — 블랙리스트

아래는 자동 리뷰가 습관적으로 만드는 오탐이다. 기본적으로 발견에서 제외한다.

- **"에러 핸들링을 추가하세요"** — 상위 호출자나 프레임워크가 이미 처리하는 경우가 대부분. 실제로 삼켜지는 경로를 `file:line`으로 짚을 수 있을 때만.
- **내부(private) 함수의 input validation 요구** — 신뢰 경계 안에서 호출되는 함수에 방어 코드를 강요하지 않는다. 외부 입력이 닿는 경계에서만.
- **잘 알려진 magic number** — `200`/`404`/`1024`/`60` 같은 관용값을 상수화하라는 지적은 노이즈.
- **exhaustive switch/case에 "함수가 길다"** — 분기 나열은 길이가 아니라 응집도로 판단.
- **의도적 fire-and-forget에 "missing await"** — 의도가 드러나면(예: 로깅, 백그라운드) 지적 아님.
- **비암호 문맥의 `Math.random()`을 보안 이슈로** — security theater. 실제 토큰/시크릿 생성일 때만.
- **포맷/import 순서/오타/린트 규칙** — 린터·포매터가 잡을 것. 리뷰 발견으로 올리지 않는다.
- **스타일 취향** — 프로젝트의 의도적 컨벤션을 "결함"으로 지적하지 않는다.
- **동적으로 참조되는 "dead code"** — 라우트명·DI 토큰·리플렉션·문자열 키로만 참조되는 심볼. unused/dead로 올리기 전 동적·문자열 참조를 grep으로 확인한다. `knip`·`vulture` 같은 검출기 결과도 이 게이트를 통과해야 발견이 된다. 확실할 때만 SAFE(즉시 제거 가능)로, 참조가 모호하면 CAUTION으로 강등해 위임 시 신중히 다룬다.

## Zero Findings는 정당한 결과

억지로 발견을 만들지 않는다. 실제로 material한 문제가 없으면 "발견 없음"이 옳은 결론이다.
단, 그 전에 diff/tests/docs/구조를 한 번 더 확인해 정말 없는지 자문한다.

## 심각도 앵커

라벨에 판정 근거를 붙인다. Impact × Likelihood로 판단하되 아래 앵커를 우선한다:

- **외부 사용자가 악용 가능한 보안 취약점** → 항상 Critical 또는 High.
- **핫패스(hot path)의 성능 결함** → 최소 Medium.
- **cosmetic/일관성 이슈** → Low를 넘기지 않는다.
- **cross-축 corroboration**: 두 독립 축이 같은 발견을 내면 심각도/확신도를 한 단계 올린다.
