# Automation Quality — 테스트 코드를 어떻게 쓸지

테스트 코드 자체의 품질 규범. 프레임워크에 독립적인 원칙만 담고, 구체 구현은 대상 repo의 관례를 따른다.
출처: ISTQB CTAL-TAE v2.0(구조·wait·fixture·검증), CTAL-TA v4.0 ch1(품질 기준, oracle, test data), CTAL-TTA v4.0 ch5(리뷰 체크리스트).

목차:

1. 테스트 케이스 품질 기준
2. 구조와 계층
3. Fixture와 격리
4. Assertion과 oracle
5. 비동기와 비결정성
6. 테스트 데이터
7. E2E/UI 특화 규범
8. 유지보수와 CI 배치

## 1. 테스트 케이스 품질 기준

CTAL-TA의 테스트 케이스 품질 기준 중 테스트 코드에서 자주 깨지는 것:

| 기준 | 깨진 모습 | 규범 |
|---|---|---|
| Necessity | 같은 behavior를 검증하는 테스트 2개 | 중복은 삭제. 케이스 하나 = behavior 하나 |
| Precision | "적절한 값이 나오면 통과" 수준의 약한 assertion | 하나의 해석만 가능한 기대값 |
| Conciseness | 수십 개 assertion이 든 거대 테스트 | 작은 테스트 다수 — 실패 지점 특정, 부분 실행, 다른 테스트를 막지 않음 |
| Completeness | 기대값·데이터가 실행 시점에야 결정됨 | 케이스만 읽어도 입력과 기대 결과를 알 수 있게 |
| Understandability | 이름이 `test1`, 실패해도 뭐가 깨졌는지 모름 | 이름에 behavior와 조건을 담는다 |

## 2. 구조와 계층

테스트 코드도 계층을 갖는다 (TAE의 TAF 계층 원칙을 일반화):

```
테스트 케이스 (behavior 서술 + assertion)
  → 도메인 헬퍼 (SUT 종속: "주문을 생성한다", "로그인한다")
    → 코어 유틸 (SUT 독립: HTTP 클라이언트, DB 헬퍼, 대기 유틸)
```

- 테스트 케이스는 도메인 헬퍼만 호출한다. 코어 유틸을 직접 호출하기 시작하면 테스트가 절차 나열로 전락하고 SUT 변경마다 전체 수정이 필요해진다.
- 같은 action 시퀀스가 3회 이상 반복되면 헬퍼로 추출하고 파라미터화한다.
- 계층은 적게 유지한다. 미리 만드는 추상화보다 반복이 확인된 뒤의 추출이 낫다.

## 3. Fixture와 격리

- 각 테스트는 **repeatable & atomic**: precondition을 스스로 만들고(setup) 흔적을 남기지 않는다(teardown). 이것이 단독 실행·임의 순서 실행·병렬 실행을 가능하게 하는 토대다.
- 공유 상태(DB, 파일, 전역, 외부 서비스)를 건드리는 테스트는 시작·종료 시 상태를 pre-defined state로 복원한다: 만든 데이터 삭제, 로그아웃, 파일 정리.
- 반복되는 precondition은 setup으로 추출하되, **테스트 이해에 필요한 값은 케이스 안에 남긴다**. setup에 모든 것을 숨기면 케이스만 읽어서 무엇이 검증되는지 알 수 없다.
- 상위 레벨 테스트의 precondition은 가능하면 하위 인터페이스로 처리한다. 예: UI 테스트의 사용자 준비를 화면 조작이 아니라 API 호출로 — 빠르고, 대상 behavior 외 실패 요인이 줄어든다.

## 4. Assertion과 oracle

- assertion은 automated test oracle의 구현체다. **assertion 없는 테스트는 실행문이지 테스트가 아니다** — 리뷰에서 가장 먼저 걸러낸다.
- 기대값은 구현과 독립적으로 산출한다. 구현 함수를 호출해 기대값을 만들면 그 테스트는 항상 통과한다(oracle 오염).
- 예상되는 차이는 비교에서 제외한다: 타임스탬프, 생성 ID, 순서 비보장 컬렉션. 이를 제외하지 않으면 flaky의 원인이 되고, 통째로 비교를 포기하면 검출력이 사라진다.
- 실패 메시지는 "기대 X, 실제 Y, 맥락 Z"가 나오게 한다. diff 없는 boolean assertion(`assert result == expected` 수준의 출력)은 디버깅 비용을 테스트 사용자에게 전가한다.
- 구조화된 응답(API 등)은 필드별 assertion을 나열하기 전에 schema 검증을 고려한다 — 필수 필드·타입을 일괄 검증하고, 개별 assertion은 behavior에 해당하는 값만.

## 5. 비동기와 비결정성

- **wait 위계** (아래로 갈수록 좋다):
  1. hard-coded sleep — 금지. 짧으면 flaky, 길면 느림. 둘 다인 경우가 보통.
  2. 폴링 + timeout — 조건을 주기적으로 확인. timeout은 필수.
  3. 이벤트·상태 구독 + timeout — 가장 좋다. 완료 신호를 직접 받는다.
- 시간 의존은 clock을 주입해 고정한다. "자정 근처에만 실패하는 테스트"는 clock 주입 부재의 증상.
- random을 쓰면 seed를 고정하거나 실패 시 seed를 로그에 남긴다. 재현 불가능한 실패는 분석 불가능한 실패다.
- **flaky 처리 절차**: 발견 → active suite에서 격리(quarantine) → 원인 분석(테스트 결함인지 제품의 race condition인지) → 수정 후 복귀. 재시도 옵션으로 덮으면 제품의 동시성 결함까지 함께 숨는다. repo에 승인된 bounded retry 정책이 있으면 그 범위는 따르되, 원인 분석 없이 재시도를 새로 추가하지 않는다.
- 테스트 실패의 원인 위치는 4곳이다: 제품, 테스트 코드, 환경/인프라, 테스트 데이터. 실패 보고 시 어느 쪽인지 구분한다(TAE의 "TAS failure" 개념). 구분 없이 "테스트 깨짐"으로 뭉치면 신뢰가 무너지고 실패가 무시되기 시작한다.

## 6. 테스트 데이터

- test logic과 test data를 분리한다. 값이 반복 hardcoding되면 외부화(파일, builder, factory)하되, 케이스 이해에 필수인 값은 케이스에 남긴다.
- 데이터는 테스트가 소유한다: 각 테스트가 자기 데이터를 만들고 지운다. 공유 데이터에 의존하면 실행 순서 결합이 생긴다.
- production 유사 데이터가 필요하면 분포·outlier를 반영하되 개인정보는 익명화/가명화한다. production 복사본을 그대로 쓰지 않는다.
- 시간이 지나면 깨지는 데이터(만료일, 나이 계산)는 상대 날짜로 생성하거나 data aging을 자동화한다. "작년에 만든 fixture가 올해 깨지는" 패턴의 예방.

## 7. E2E/UI 특화 규범

- **locator는 한 곳에**: Page Object(화면 단위) 또는 그 위의 Flow Model(사용자 행동 단위)로 모은다. 화면 구조가 바뀌면 한 곳만 고친다. 테스트 케이스 안에 selector가 흩어져 있으면 UI 변경마다 전 케이스 수정이 필요하다.
- 테스트용 안정 식별자(test id 등)를 SUT에 요구하는 것은 정당하다 — testability(observability/controllability)는 SUT의 non-functional 요구사항이다. CSS 구조나 텍스트에 의존하는 locator는 깨지기 쉽다.
- 실패 시 재현 가능한 산출물을 남긴다: 스크린샷, 실패 시점 로그, 실행한 action 기록. E2E 실패는 로그 없이는 재현이 불가능한 경우가 많다.
- suite가 커지면 목적별 분리를 검토한다. 예: 빠른 smoke는 배포 게이트, 전체 regression은 주기 실행. 전부를 매 커밋에 돌리면 피드백이 느려져 테스트가 무시된다.

## 8. 유지보수와 CI 배치

- 테스트 코드에도 제품과 동일한 static analysis·lint·리뷰를 적용한다. 테스트 안의 하드코딩된 credential, 죽은 헬퍼, 중복 블록도 동일한 결함이다.
- 리뷰 시 defensive 항목 (CTAL-TTA 리뷰 체크리스트에서 테스트 코드에 해당하는 것):
  - 부동소수점 동등 비교 금지(허용 오차 비교로)
  - 외부 리소스 접근에 timeout과 에러 처리
  - 파일·연결 등 리소스는 실패 경로에서도 정리
  - unreachable 테스트(조건상 절대 실행 안 되는 분기) 제거
- CI 배치는 피드백 속도 기준으로 정하되, 기존 CI 구조가 있으면 그 관례가 우선이다. 예: 커밋마다 unit/component, 통합 지점은 CI 파이프라인, 느린 E2E·non-functional은 배포 게이트나 nightly. 빠른 층이 깨지면 뒤 층은 돌리지 않는다.
- 회귀 스위트는 늘어나기만 하는 자산이 아니다: 커버 영역이 겹치는 케이스, 더 낮은 레벨로 내려갈 수 있는 케이스, 잡는 결함이 없어진 케이스를 주기적으로 정리한다(tests wear out).
